## Preparação F1 mínima (mecanismos existentes)

### Diferenciação de executores (ajuste documental 2026-10-28)

O driver `Invoke-OrchestrationAutonomousObjective` suporta DOIS modos de execução, que NÃO são equivalentes:

| Modo | Mecanismo | O que comprova | O que NÃO comprova |
|---|---|---|---|
| **Executor injetado (harness)** | `-Executor` recebe um scriptblock/stub que simula o dispatch | Plumbing dos gates (prepare/claim/settle/continuation) | Invocação nativa real do subagent |
| **DispatchIntent (cooperativo)** | Sem `-Executor`, o driver retorna `dispatch_intent` para o Planner | Contrato de intent + recibos | Execução real do worker |
| **Chamada nativa real** | O Planner invoca a ferramenta `subagent` nativa do OpenCode V2 | Execução real do worker (RUNTIME_REAL) | Correlação com Kernel (requer settle) |
| **Resultado reconciliado** | O Planner chama `objective-step settle` com o envelope + worker-result | Correlação worker result ↔ Kernel (verified_pass, DONE, COMPLETED) | — |

**Sequência completa para certificação real:**
1. Driver (sem Executor) → `dispatch_intent` → Planner recebe intent.
2. Planner invoca `subagent` nativo → worker executa → resultado.
3. Planner chama `objective-step settle` → Kernel valida envelope + worker-result → candidate.
4. Kernel verifica (verified_pass) → review (se exigido) → DONE → COMPLETED.

### Parâmetros reais do driver (API existente, sem parâmetros inventados)

Parâmetros de `Invoke-OrchestrationAutonomousObjective`:
- `$Goal` (object, in-memory) ou `$GoalId` + `$GoalStoreDir` (persistente)
- `$MaxSteps` (int, 1-100): limite de steps de orquestração
- `$MaxDispatches` (int, 0-100): limite de despachos com efeito
- `$CheckpointDir` (string): diretório de checkpoints
- `$Executor` (object, nullable): executor injetado (harness) ou null (cooperativo)
- `$Authorization` (object): autorização explícita (nunca sintetizada)
- `$DispatchSpec` (object): spec de dispatch
- `$ResumeCheckpointId` (string): checkpoint para retomada
- `$EvidenceStoreDir` (string): diretório de evidências
- `$ReceiptDir` (string): diretório de recibos (prepare/claim/settle)
- `$RepoRoot` (string): raiz do repositório
- `$TasksDir` (string): diretório de tasks
- `$FlagsPath` (string): caminho das flags
- `$ControllerPath` (string): caminho do controller

**Não existe** parâmetro `SessionId`, `TokenBudget` ou `DurationLimit` no driver. Esses são controlados externamente (watchdog, MaxSteps, MaxDispatches).

### Orçamento (mecanismos existentes, sem novos componentes)

| Controle | Mecanismo existente | Limite verificável | Limitação |
|---|---|---|---|
| Tentativas de certificação | MaxSteps (1-100) | 1 execução real (definido antes) | Parâmetro documentado, não enforcement automático |
| Dispatches com efeito | MaxDispatches (0-100) | 1-2 para jornada mínima | Saldo verificado ANTES do dispatch (F5) |
| Passos de orquestração | MaxSteps (1-100) | 3-5 para jornada mínima | Driver sincrono, sem polling |
| Consumo de tokens | Watchdog budget (wall_clock_seconds, no_progress_seconds) | Configurável via policy (execution-budget-policy.json) | Tokens não controlados diretamente; watchdog controla duração |
| Duração máxima | Watchdog (wall_clock_seconds) + MaxSteps | Configurável via policy (600-3600s) | Interrupção via watchdog (HARD_TIMEOUT) |
| Fallbacks para modelos pagos | Model routing (T0-T4) | T0 determinístico (sem LLM), T1-T4 por papel | Roteamento por política, não por orçamento |
| Interrupção | Watchdog (HARD_TIMEOUT, NO_PROGRESS) | Automática via watchdog | Requer binding de processo (ENFORCE) |

**Limitação declarada:** Tokens não são controlados diretamente pelo driver. O controle de duração é feito pelo watchdog (wall_clock_seconds). O controle de passos é feito por MaxSteps. O controle de dispatches é feito por MaxDispatches. Não confundir parâmetro documentado com controle aplicado.
